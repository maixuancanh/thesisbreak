# Walrus Memory adapter

`packages/integrations/src/memwal.ts` binds the official Apache-2.0 `@mysten-incubation/memwal@0.1.9` SDK. It uses `MemWal.create`, `rememberAndWait`, `recall`, `restore`, and `destroy`; signing, encryption, embedding and Walrus upload remain upstream SDK/relayer responsibilities. Installed SDK declarations were inspected. Node >=20 is supported upstream; this workspace runs Node 24. Required Sui/Seal peers are resolved in the lockfile; optional AI and Walrus peers are not needed for this API.

This module imports Node crypto and rejects browser execution at import and operation boundaries. Import it only into server modules. Do not expose its configuration, factory, client, or namespace selection to browser code. Set `MEMWAL_DELEGATE_KEY`, `MEMWAL_ACCOUNT_ID` (full Sui object ID), and optionally `MEMWAL_RELAYER_URL` (HTTPS; official default is `https://relayer.memory.walrus.xyz`). The parser reads only these explicit fields and never discovers credentials from other products. The upstream SDK validates the delegate key encoding. Authentication and account ownership must be checked by the server before constructing an adapter with its trusted user ID. This adapter does not supply authentication.

Each trusted user gets a deterministic SHA-256 namespace. Namespace selection is not accepted from request data. The namespace is an isolation filter, not a cryptographic authorization boundary against someone possessing the shared delegate key. Do not expose raw SDK account-wide enumeration APIs.

Records contain schema 1, logical ID, server user ID, type, version, persisted recordedAt, JSON payload and a SHA-256 hash of JSON with ordinal UTF-16 key sorting (without Unicode normalization). The caller must persist the same timestamp and record content for a retry. Idempotency keys use namespace, logical ID and version; changing content without incrementing version intentionally retains the same key, allowing the official relayer to reject the conflict. The hash detects corruption but is not a signature or proof of authorship.

A write is `verified` only after recall returns the same validated envelope/hash and exact serialized text from the receipt's blob ID. An identical older blob cannot verify a new receipt. Recall preserves source blob references only for validated hits in the trusted user namespace; conflicting records have all sources excluded. A blob ID reported with different valid plaintexts is excluded before logical-record deduplication; an independent consistent blob copy may still be used. Neither write verification nor recovery inventory checks accept conflicted blob sources. Missing top-20 readback is `pending`, not proof of absence. Transport/write/readback failures return `error` with a fixed reason that cannot expose SDK credential-bearing errors. Callers must retain pending/error work for a later retry; this package has no outbox worker. Recall validates distance (<0.5), schema, user, hash and deduplicates logical ID/version; conflicting envelopes are excluded. Search results are never represented as a complete inventory.

`restore` reports the SDK's recovery counts. Truncation or failures mean incomplete; otherwise completeness remains unknown unless a caller-provided expected inventory has been checked item by item. Recovery collects validated source observations across all inventory recalls before deciding completeness, globally quarantining blob IDs with conflicting plaintexts and logical IDs/versions with conflicting envelopes. `expected_inventory_verified` covers only that explicit inventory and does not assert a complete account archive. `listMemories` provides metadata upstream, not plaintext reconstruction, and is deliberately not exposed. `destroy` wipes the SDK client's key material and disables adapter calls; it is not physical deletion of stored records. No unsupported deletion or storage renewal API is implemented.

Unit tests use an explicitly offline injected transport fake to exercise isolation and validation. They do not establish live relayer compatibility, encryption, on-chain storage, persistence, account authorization, Mainnet readiness or rewards. No credentials or live write were used. Outbox processing, authenticated service integration and a separately authorized Mainnet evidence gate remain later work.
